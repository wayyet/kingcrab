## 3. 对话可用性测试（POST /v1/chat/completions）

**测试请求**：

```json
{
  "model": "<模型ID>",
  "messages": [{ "role": "user", "content": "请用一句话回答：1+1等于几？" }],
  "max_tokens": 100,
  "stream": false
}
```

`Qwen3.6-27B` 因思考链较长，额外用 `max_tokens: 800` 复测确认。

### 3.1 可用模型（2/11）

| 模型 | HTTP | 结果 | 备注 |
|------|------|------|------|
| `MiniMax-M2.7` | 200 | ✅ 正常输出 `1+1等于2。`，finish_reason=stop | 完全可用 |
| `Qwen3.6-27B` | 200 | ✅ 输出 `1+1等于2。` | 思考链约 200+ token，需给足 max_tokens 才会输出正式内容；`max_tokens=16/100` 时会因思考被截断而看不到正式回复 |

### 3.2 不可用模型（9/11）

| 模型 | HTTP | 错误码 | 错误信息（原文要点） | 归类 |
|------|------|--------|----------------------|------|
| `gpt-5.2` | 401 | `upstream_error` | Access denied due to invalid subscription key or wrong API endpoint | Azure 通道上游 Key/Endpoint 失效 |
| `deepseek-v4-pro` | 401 | `upstream_error` | 同上 | Azure 通道上游 Key/Endpoint 失效 |
| `deepseek-v4-flash` | 401 | `upstream_error` | 同上 | Azure 通道上游 Key/Endpoint 失效 |
| `glm-5.2` | 401 | `invalid_api_key` | Incorrect API key provided | OpenAI 兼容上游 Key 无效 |
| `glm-5.1` | 401 | `invalid_api_key` | 同上 | OpenAI 兼容上游 Key 无效 |
| `kimi-k2.6` | 401 | `invalid_api_key` | 同上 | OpenAI 兼容上游 Key 无效 |
| `qwen3.6-plus` | 401 | `invalid_api_key` | 同上 | OpenAI 兼容上游 Key 无效 |
| `glm-4.7` | 401 | `invalid_api_key` | 同上 | OpenAI 兼容上游 Key 无效 |
| `qwen3.6-flash` | 401 | `invalid_api_key` | 同上 | OpenAI 兼容上游 Key 无效 |

**关键观察**：

1. **`GET /v1/models` 全部成功**，但 **`POST /v1/chat/completions` 9/11 失败**——印证了设计文档 §4.2 的核心判断：**模型列表可用 ≠ 对话推理可用**。
2. 失败集中在两类上游错误，与网关侧 Provider/Endpoint 配置无关（测试是直连上游，未经过 kingcrab Gateway）：
   - `upstream_error`（Azure 通道）：`gpt-5.2`、`deepseek-v4-pro`、`deepseek-v4-flash`
   - `invalid_api_key`（OpenAI 兼容通道）：GLM 全系、Kimi、Qwen 两模型
3. `MiniMax-M2.7` 与 `Qwen3.6-27B` 可正常对话，说明该 new-api 账号**部分渠道配置有效**，非整体 Key 失效。

## 4. 与设计文档的对照结论

| 设计文档结论 | 本次实测 | 判定 |
|--------------|----------|------|
| §5.1 R7「上游 chat 失败」**待验证** | `gpt-5.2` 实测 401 上游失败 | ✅ **已证实**：根因在 new-api 平台渠道配置（Azure 通道 subscription key/endpoint 失效），非网关配置问题 |
| §5.1 R1「Provider 与 Model 错配」 | 无法通过上游直连判定 | 需在网关层复测（`--doctor`） |
| §5.1 R2「SupportsTools=false」 | 无法通过上游直连判定 | 需在网关层复测 |
| §5.2 MiniMax 相关（api.minimaxi.com） | 本次未测（不在 new-api 端点内） | 沙箱 `MiniMax-M2.5` 需另测 `https://api.minimaxi.com/v1` |

**结论**：`gpt-5.2` 当前不可用的**直接原因是 new-api 平台侧上游渠道失效**，需要登录 new-api 管理后台检查/刷新对应渠道的 API Key 与 Endpoint；网关侧配置问题（Provider/SupportsTools）作为次要因素仍需在网关层验证。

---

## 5. 建议

1. **P0 - 平台侧修复**：登录 new-api 管理后台，检查 `gpt-5.2`/`deepseek-v4-*`（Azure 通道）与 GLM/Kimi/Qwen 等渠道的上游 Key 与 Endpoint 是否失效，重新配置后重跑本报告测试。
2. **P1 - 密钥轮换**：本测试所用 Key 已在项目文档/git 历史明文暴露，建议立即轮换，并将配置改为 `env:MODEL_PROVIDER_KEY` 方式注入。
3. **P2 - 网关侧验证**：待上游修复后，执行设计文档 §6.6 的 `dotnet run -- --doctor`，验证 Provider/SupportsTools 链路；当前 appsettings 中 Provider=`deepseek` 仍会导致工具被禁（设计文档 R2），应改为 `openai-compatible`。
4. **P3 - 备选模型**：若急需可用模型，可先用 `MiniMax-M2.7` 或 `Qwen3.6-27B`（注意后者需给足 max_tokens）。
5. **建立冒烟标准**：将本报告的 chat 冒烟脚本纳入 CI/运维，避免「models 可用、chat 不可用」的监控盲区。

## 附录：测试脚本参考（PowerShell）

```powershell
# 列模型
curl.exe -s --ssl-no-revoke "https://new-api.ai4c.cn/v1/models" -H "Authorization: Bearer $env:LLM_API_KEY"

# 对话冒烟（单模型）
$body = @{
  model = "gpt-5.2"
  messages = @(@{ role = "user"; content = "ping" })
  max_tokens = 16
  stream = $false
} | ConvertTo-Json -Depth 6
curl.exe -s --ssl-no-revoke "https://new-api.ai4c.cn/v1/chat/completions" `
  -H "Authorization: Bearer $env:LLM_API_KEY" `
  -H "Content-Type: application/json" `
  -d $body
```

> 备注：本机 Windows 执行时 TLS 握手可能报 `CRYPT_E_REVOCATION_OFFLINE`，需加 `--ssl-no-revoke` 参数跳过吊销检查。
