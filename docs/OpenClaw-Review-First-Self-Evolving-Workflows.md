# OpenClaw 审查优先的自演化工作流

> 来源: https://zread.ai/clawdotnet/openclaw.net/26-review-first-self-evolving-workflows

## 概述

OpenClaw 的学习子系统通过观察 agent 会话来检测重复的行为模式——偏好声明、重复出现的提示词以及多工具调用链——然后提出自我演化产物（配置文件更新、自动化规则、技能），这些产物在生效前需要明确的人工审核**。这种设计在模式检测与系统突变之间强制执行了必要的人在环路（human-in-the-loop）门控，确保 agent 绝不会悄无声息地修改自身行为。

---

## 1. 架构概述

学习管道作为一个**回合后（post-turn）观察层**运行，不同于[工具审批与钩子](/16-tool-approval-and-hooks)中描述的实时工具执行与审批路径。

| 对比维度 | 工具审批 | 学习审核 |
|---------|---------|---------|
| **运行时机** | 实时（每次工具调用前） | 回合后（post-turn） |
| **控制内容** | 单个工具调用 | Agent 长期行为的结构性变更 |
| **风险级别** | 中等 | 较高 |
| **门控方式** | ToolApprovalService | 管理 API + CSRF 防护 |

工具审批控制的是**单个工具的调用**，而学习系统控制的是 **agent 长期行为的结构性变更**——这是一类具有更高风险的突变，需要其专属的审核门控。

---

## 2. 提案类型与检测逻辑

`LearningService` 将检测到的模式分为三种提案类型，每种类型都有不同的检测阈值、置信度模型和审批副作用。

### 2.1 配置文件更新提案

配置文件提案由**编译后的正则表达式**触发：

```
\b(i prefer|call me|my name is|i like)\b
```

该表达式用于匹配会话中最后的用户消息。

#### 检测逻辑

1. **触发条件**：对偏好/身份短语进行正则匹配
2. **去重保护**：
   - 如果用户现有配置文件中已包含该内容
   - 或者针对同一参与者已存在待处理的 `profile_update` 提案，则会跳过
3. **生成的 UserProfile**：
   - 低置信度事实（0.55，刻意设低——偏好声明往往存在噪声）
   - 将完整的用户消息作为偏好
   - 上限为 240 个字符

| 方面 | 细节 |
|------|------|
| **触发条件** | 对偏好/身份短语进行正则匹配 |
| **置信度** | 固定 0.55（刻意设低——偏好声明往往存在噪声） |
| **去重机制** | 检查现有配置文件 + 每个参与者的待处理提案 |
| **审批时操作** | 将 `UserProfile` 写入 `IUserProfileStore` |
| **自动应用** | 在 `ReviewRequired = false` 时受支持 |

### 2.2 自动化建议提案

自动化提案通过**查询 `ISessionSearchStore`**，检测来自相同渠道和发送方的语义相似历史消息，从而识别重复出现的提示词。

#### 检测逻辑

1. **触发条件**：会话搜索结果数量 ≥ `AutomationProposalThreshold`（默认为 3）
2. **置信度计算**：随匹配量线性增长

```
置信度 = min(0.9, 0.3 + matchCount × 0.1)
```

- 达到阈值时：0.4
- 匹配 6 次及以上时：0.9

3. **生成的自动化草稿**：
   - 计划任务设为 `@daily`
   - `IsDraft = true`
   - 标记为 `"suggested"` 和 `"learning"`

| 方面 | 细节 |
|------|------|
| **触发条件** | 会话搜索结果数量 ≥ `AutomationProposalThreshold` |
| **置信度** | 线性：0.3 + (matchCount × 0.1)，上限为 0.9 |
| **自动化状态** | `Enabled = false`，`IsDraft = true`，`Source = "learning"` |
| **审批时操作** | 保存至 `IAutomationStore`（仍处于禁用状态——需要单独激活） |
| **自动应用** | 不支持——始终进入待处理状态 |

### 2.3 技能草稿提案

技能���案是**最复杂的检测路径**。它们通过从每次包含超过 1 个工具调用的助手回合中构建序列字符串，然后统计出现次数。

#### 示例工具序列

```json
"web_search -> file_read -> edit_file"
```

#### 检测逻辑

1. **触发条件**：工具序列重复次数 ≥ `SkillProposalThreshold`（默认为 2）
2. **草稿生成**：利用 LLM 将该工作流总结为 `SKILL.md` 文档
   - 10 秒超时
   - 附带模板降级方案

#### 验证门控

草稿内容在审批时会经过全面的验证门控：

| 验证项 | 说明 |
|--------|------|
| **前置元数据验证** | 结构验证 |
| **内容哈希完整性** | SHA-256，用于检测审核与审批之间是否被篡改 |
| **路径遍历防护** | 检测 `..` 和空字节 |
| **长度上限** | 4000 字符 |

#### TOCTOU 防护

技能草稿使用 **SHA-256 内容哈希**：
1. 在创建提案时，将哈希存储为 `DraftContentHash`
2. 审批时，系统根据当前的 `DraftContent` 重新验证该哈希
3. 如果两者不一致，审批将被拒绝并提示"技能草稿内容不再与已审核的提案匹配"

这可以防止 **TOCTOU（检查时间/使用时间）攻击**，避免提案内容在审核与审批之间被替换。

| 方面 | 细节 |
|------|------|
| **触发条件** | 会话中相同的工具序列重复 ≥ `SkillProposalThreshold` 次 |
| **置信度** | 线性：0.4 + (repeatCount × 0.1)，上限为 0.95 |
| **草稿来源** | LLM 总结（10 秒超时），附带模板降级方案 |
| **审批时操作** | 将 `SKILL.md` 写入 `~/.openclaw/skills/<id>/`，然后触发 `runtime.ReloadSkillsAsync()` |
| **验证机制** | 前置元数据结构、哈希完整性、长度上限、路径遍历防护 |

## 3. 配置模型

`LearningConfig` 类暴露了四个配置项，挂载在 `GatewayConfig` 的 `Learning` 配置节下。

### JSON 配置示例

```json
{
  "Learning": {
    "Enabled": true,
    "ReviewRequired": true,
    "SkillProposalThreshold": 2,
    "AutomationProposalThreshold": 3,
    "MaxDraftChars": 4000
  }
}
```

### 配置项说明

| 属性 | 类型 | 默认值 | 用途 |
|------|------|--------|------|
| `Enabled` | `bool` | `true` | 整个学习子系统的主开关 |
| `ReviewRequired` | `bool` | `true` | 设为 false 时，配置文件更新将自动应用；技能/自动化提案仍会进入待处理状态 |
| `SkillProposalThreshold` | `int` | 2 | 生成技能草稿前，工具序列所需的最小重复次数 |
| `AutomationProposalThreshold` | `int` | 3 | 生成自动化建议前，会话搜索所需的最小匹配次数 |
| `MaxDraftChars` | `int` | 4000 | 生成的技能草稿内容的最大字符长度 |

### 自动应用规则

当 `ReviewRequired` 被禁用时：
- **profile_update 提案**：直接写入配置文件存储，记录为自动审批
- **技能和自动化提案**：始终**需要明确的审批**，无论此设置如何

这反映了自动应用结构性变更具有更高的风险。

## 4. 提案生命周期

每个学习产物都会流经三态生命周期：

```
pending → approved / rejected
```

### LearningProposal 模型

| 字段 | 用途 |
|------|------|
| `SourceSessionIds` | 用于审计追踪 |
| `Confidence` | 用于优先级排序 |
| `CreatedAtUtc` | 用于新鲜度检查 |
| `UpdatedAtUtc` | 用于新鲜度检查 |
| `ReviewedAtUtc` | 用于治理问责 |
| `ReviewNotes` | 用于治理问责 |

## 5. 管理 API 界面

学习子系统通过管理 API 暴露了三个端点，所有的变更操作均受操作员身份验证保护，并带有 CSRF 防护。

### 端点列表

| 端点 | 方法 | 鉴权 | 用途 |
|------|------|------|------|
| `/admin/learning/proposals` | `GET` | 读取 | 列出提案，支持可选的 `?status=` 和 `?kind=` 过滤��� |
| `/admin/learning/proposals/{id}/approve` | `POST` | CSRF | 执行提案的副作用并标记为已批准 |
| `/admin/learning/proposals/{id}/reject` | `POST` | CSRF | 标记为已拒绝，可附带可选的 `{ "reason": "..." }` 请求体 |

### 审批副作用

审批端点会将 `IAgentRuntime` 引用传递给 `LearningService.ApproveAsync`，这对于技能提案至关重要：

1. 将 `SKILL.md` 文件写入托管技能目录（`~/.openclaw/skills/<id>/`）
2. 调用 `runtime.ReloadSkillsAsync()` 将技能热重载到运行中的 agent 内

这将学习系统直接连接到 **SkillLoader** 管道，新技能会以 `SkillSource.Managed` 的优先级进入其中。

### 审计日志

所有变更操作都会通过 `RuntimeEventEntry` 追加到运行时事件日志中：
- 组件标记为 `"learning"`
- 动作为 `"approved"` 或 `"rejected"`
- 确保与其他系统事件一起实现完全的可审计性

## 6. 与治理层的关系

学习子系统运行的抽象层级与工具执行钩子不同，但共享着**绝不信任自主突变**的相同安全理念。

### 对比表

| 关注点 | 工具审批（每次调用） | 学习审核（每次产物） |
|--------|---------------------|----------------------|
| **作用域** | 单个工具调用 | 结构性行为变更 |
| **门控** | 带有超时机制的 `ToolApprovalService` | 带有 CSRF + 操作员鉴权的管理 API |
| **存储** | 内存中的 `ConcurrentDictionary` | 持久化的 `ILearningProposalStore` |
| **审计** | `ApprovalAuditStore` + `AuditLogHook` | `RuntimeEventEntry` + `OperatorAuditEntry` |

### AutonomyHook

- `AutonomyHook` 在工具层面强制执行只读/监督/完全自主模式
- 学习系统在**演化**层面强制执行先审后批

### 技能与合约的集成

通过学习系统审批的技能，会通过 `SkillPromptBuilder.Build()` 成为 agent 提示词的一部分：
- 将 `<skills>` XML 注入到系统提示词中
- 学习到的技能从根本上改变了 agent 的行为指令

### ContractScopeHook

`ContractScopeHook` 可以在受合约约束的会话中进一步限制已学习技能的效果：
- `ScopedCapabilities`：限制其工具链能够访问的文件系统路径
- `MaxToolCalls`：限制该工作流可用的工具调用总预算

## 7. 存储接口

`ILearningProposalStore` 定义了一个极简的 CRUD 界面：

| 方法 | 说明 |
|------|------|
| `ListProposalsAsync` | 支持状态/类型过滤的列表查询 |
| `GetProposalAsync` | 按 ID 获取单个提案 |
| `SaveProposalAsync` | 用于创建和状态转换 |

该存储实例在组合时通过 `FeatureFallbackServices.ResolveLearningService()` 解析，允许不同的实现（基于文件的、SQLite 等）作为同一接口的后端，而无需修改学习逻辑。

│  │ 2. 自动化提案 (会话搜索)                               │   │

                      ▼
┌─────────────────────────────────────────────────────────────────┐
│                     提案状态: pending                           │
│  ┌─────────────────────────────────────────────────────┐     │
│  │ 进入待处理队列 → 等待人工审核                         │     │

                            ▼
         ┌─────────────────┴─────────────────┐
         ▼                                   ▼

│    审批 (approve)    │              │    拒绝 (reject)    │
