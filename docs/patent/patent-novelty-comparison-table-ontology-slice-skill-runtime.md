# 发明点对比现有技术表：本体切片到技能运行时正式输入

## 一、使用说明

本文用于和专利代理人快速沟通本方案相对于现有技术的区别点、新颖点和创造性抓手。阅读重点不是具体实现文件，而是“任务导向本体切片 -> 投影文件 -> 契约 路由 -> 阻断 -> 技能运行时 注入”这一整条控制链路。

## 二、对比表

| 对比维度 | 现有技术常见做法 | 现有技术不足 | 本发明方案 | 可能的新颖点/创造性表达 | 建议保护位置 |
| --- | --- | --- | --- | --- | --- |
| 1. 本体 的运行时使用方式 | 直接把完整 本体、摘要或人工整理说明拼接到 提示，或仅作为离线知识材料使用 | 输入过大、运行时自行裁剪、无关语义混入、术语边界不能直接成为控制输入 | 先围绕当前任务抽取 任务导向本体切片，仅保留 概念、关系、约束、来源 等最小语义闭包，再进入后续运行链路 | 不直接消费完整 本体，而是先按任务收缩为最小语义闭包，再作为后续运行时输入基础 | 独立权利要求核心步骤；从属可补 本体切片 字段组成 |
| 2. 本体切片 的工程地位 | 局部抽取结果常是 Markdown、JSON、评审附件或设计草稿 | 只是知识整理产物，不能成为 消费技能 的正式输入 | 将 本体切片 明确作为中间语义层，继续投影为面向 消费 的 投影文件 | 将 本体切片 从离线知识产物提升为运行时正式输入链路中的中间契约层 | 独立权利要求核心步骤 |
| 3. 本体切片 到 消费 的转换方式 | 由开发者手工改写 提示、模式 或 工作流，缺少统一转换层 | 同一语义子图难以复用，且不同下游结果容易漂移 | 引入 定向 投影文件 机制，把同一 本体切片 投影为 领域模型视图、数据结构约束视图、提示约束视图、工作流契约视图 等 目标视图 | 同一任务语义闭包可面向多种运行时消费视图稳定交付 | 独立权利要求核心步骤；从属覆盖多 目标视图 |
| 4. 契约 的组织方式 | 投影文件 文件即使存在，也常零散存放，仅供人工阅读 | 运行时不知道有哪些 主题、目标视图 和可用路径 | 通过 契约索引 统一组织 生产方、主题、目标视图、路径、评分规则和默认策略 | 用 机器可读 路由入口把散落 投影文件 组织为可被运行时自动选择的契约集合 | 独立权利要求核心步骤；从属覆盖 契约索引 字段 |
| 5. 契约 发现方式 | 依赖人工配置、硬编码加载或测试手工构造 | 无法自动发现、无法稳定绑定、缺少诊断能力 | 技能加载器 自动扫描 契约索引 并绑定到 技能 定义 | 将 契约 从静态目录资产转化为 技能加载器 可发现、可绑定、可诊断的运行时输入源 | 从属权利要求；也可写入主权作为组合链条一环 |
| 6. 主题 选择时机 | 常在 技能 重载 阶段固化，或依赖默认 主题 | 同一 技能 难以针对不同请求动态切换主题 | 主题 选择在 请求时 执行，根据当前请求内容对候选 主题 评分和选择 | 主题选择依赖当前请求而非静态配置，是请求级动态路由机制的一部分 | 独立权利要求核心步骤 |
| 7. 目标视图 选择时机 | 常使用固定 目标视图 或人工指定 目标视图 | 无法根据当前请求在模型约束、结构校验、工作流表达之间切换 | 在已选 主题 内继续对 目标视图 评分和选择 | 双层路由，不仅选 主题，还在 主题 内动态选 目标视图 | 独立权利要求核心步骤；从属覆盖 差距 阈值/歧义 判定 |
| 8. 运行时对不确定性的处理 | 通常继续执行、静默降级或回退默认模板 | 错误边界扩大，结果不可解释、不可审计 | 在 主题歧义、目标视图歧义、投影文件 缺失、解析失败、未决问题 未解、状态不可消费等情况下执行 阻断检查 | 将“不确定时阻断”制度化为 技能运行时 正式治理机制，而不是人工经验 | 独立权利要求核心步骤；从属覆盖 阻断 条件 |
| 9. 投影文件 的进入 技能运行时 方式 | 即使有 投影文件，也常停留在文档层 | 投影文件 不进入真正运行链路 | 仅在 路由 成功且通过 阻断检查 后，将 投影文件 转换为 提示补丁、守卫约束 或其他 技能运行时 输入并注入 技能运行时 | “阻断检查通过后才能注入 技能运行时”的串联控制链，是区别于静态模板的重要特征 | 独立权利要求核心步骤 |
| 10. 多 生产方 支持方式 | 单来源假设、最后写入覆盖或简单优先某一来源 | 多来源并存时容易失控，无法解释为何选某一结果 | 各 生产方 分别 路由解析，再按 评分值 和 生产方优先级 排序；完全同分则阻断 | 多 生产方 的“内容评分优先 + 生产方优先级 次级裁决 + 同分阻断”合流机制 | 从属权利要求重点；必要时可并入主权增强区别性 |
| 11. 治理边界 | 生产方 模板、技能运行时 契约 和运行时代码消费边界经常混用 | 模板合法不等于运行时可消费，文档与实现口径易漂移 | 生产方 模式 与 技能运行时 契约 模式 分层治理，离线生成校验与在线消费校验分开 | 将离线模板治理与在线消费治理显式分层，提升可审计性与工程稳定性 | 从属权利要求重点 |
| 12. 诊断与审计 | 大多缺少发现状态、阻断原因和 同分裁决 依据 | 难以排查“为什么没命中”或“为什么被阻断” | 输出 发现 发现诊断信息、路由 评分、阻断原因和多 生产方 同分裁决 依据 | 运行时路由不是黑盒，而是具备可追踪、可解释的诊断面 | 从属权利要求或说明书效果部分 |

## 三、最值得代理人抓住的 5 个区别点

1. 不是直接使用完整 本体，而是先抽取 任务导向本体切片。
2. 不是把 本体切片 当文档，而是进一步投影成面向 消费技能 的 投影文件。
3. 不是静态模板接线，而是用 契约索引 + 技能加载器发现 + 请求时 路由 形成正式运行链路。
4. 不是遇到不确定性继续执行，而是通过 阻断检查 正式阻断。
5. 不是单来源假设，而是支持多 生产方 的受控裁决与同分阻断。

## 四、建议代理人优先主张创造性的表达方式

建议不要把创造性表述压缩成“使用 JSON 文件”、“使用 模式 校验”或“增加一个索引文件”，而应围绕以下组合关系主张：

1. 任务导向最小语义闭包抽取。
2. 面向不同 目标视图 的投影交付。
3. 基于 契约索引 的运行时自动发现与请求级路由。
4. 路由 成功前必须经过 阻断检查。
5. 投影文件 仅在通过阻断检查后才能成为 技能运行时 正式输入。

上述五点组合起来，更能体现本发明不是文档组织方式的变化，而是运行时控制机制的变化。

## 五、代理人沟通建议

### 1. 适合写进独立权利要求的内容

1. 本体 -> 本体切片 -> 投影文件 -> 契约索引 -> 请求时 路由 -> 阻断 -> 技能运行时 注入 这条链路。
2. 主题 与 目标视图 的双层动态选择。
3. 阻断检查通过后才能将 投影文件 注入 技能运行时 的关系。

### 2. 适合写进从属权利要求的内容

1. 本体切片 字段组成。
2. 目标视图 类型。
3. 契约索引 的字段组成。
4. 歧义 判定与 差距 阈值。
5. 阻断 的触发条件。
6. 多 生产方 的 评分值 和 生产方优先级 排序规则。
7. 发现诊断信息 状态。
8. 生产方 模式 与 技能运行时 契约 模式 分层治理。

### 3. 不建议写得过窄的内容

1. 不要限定为某一个具体 技能 名称。
2. 不要限定为某一个固定目录结构或文件名。
3. 不要把创新点写成单一评分公式或具体分值。
4. 不要把保护重点写成某一种 JSON 字段命名。

## 六、一句话结论

本发明相对现有技术的实质区别，不在于“增加了一份语义文档”，而在于“建立了一条把任务导向 本体切片 受控转化为 技能运行时 正式输入的请求级路由与阻断治理链路”。
